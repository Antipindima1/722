# Skill: AsyncAPI Design

## Когда применять

Применяй для документирования Kafka, AMQP, MQTT, WebSocket и других message-driven каналов, событий, команд и подписок.

## Что взять на вход

### Обязательный вход
1. **Story / задача Jira**: ключ, summary, описание, критерии приёмки, комментарии с решениями, связанные задачи и ссылки на Epic (если имеются).
2. **Knowledge**: релевантные разделы `knowledge/README.md`, `01-glossary.md`, `02-business-rules.md`, `03-assumptions.md`.
3. **Запрос пользователя**: какой результат нужен, для кого, в каком формате и в каких границах.

### Дополнительный вход
- существующие диаграммы и спецификации;
- ограничения и стандарты проекта, зафиксированные в Jira или `knowledge`;
- фактическая структура репозитория и выбранные форматы файлов;
- связанные требования и решения.

Если Jira Story для задачи не существует, не выдумывай её: используй явно указанный пользователем контекст и отметь ограничение. Если входных данных недостаточно для достоверного результата, сначала задай вопрос.

## Общие правила источников

- Факты о конкретном проекте и требованиях бери только из Jira и `knowledge`, согласно корневому `AGENTS.md`.
- `knowledge/03-assumptions.md` используй с учётом статуса каждого допущения: неподтверждённое допущение не является утверждённым требованием.
- Репозиторий и код используй для определения существующей структуры, форматов и фактической реализации. Не выводи из реализации новые бизнес-требования.
- Официальные спецификации (например, OpenAPI, AsyncAPI, BPMN, UML, C4, DBML) используй только для корректности нотации и формата, а не как источник фактов о проекте.
- Для существенных утверждений сохраняй ссылку на Jira issue key или путь к документу `knowledge`.
- Если источники отсутствуют, недоступны или противоречат друг другу, обозначь пробел и задай конкретный вопрос. Не заполняй его догадкой.

## Шаги работы

1. Определи приложение/сервис в фокусе, его роль (producer, consumer или обе) и используемый протокол из Jira/knowledge.
2. Проверь существующую версию AsyncAPI и формат проекта; не мигрируй с 2.x на 3.x или обратно без согласования.
3. Определи servers, channels/addresses, operations и направление send/receive согласно версии AsyncAPI.
4. Для каждого сообщения опиши имя, payload, headers, content type, correlation ID и schema — только если определены источниками.
5. Для Kafka и аналогичных брокеров фиксируй topic, key, partitioning, ordering, consumer group, retention и delivery semantics только если они подтверждены.
6. Опиши event name/type, envelope, versioning и совместимость схем при наличии требований.
7. Retry, timeout, backoff, DLQ, deduplication, idempotency, late/duplicate event и error handling добавляй только при подтверждении.
8. Не выводи зеркальную спецификацию producer и consumer автоматически: описывай фактические операции конкретного приложения.
9. Сверь события с sequence diagram, OpenAPI и статусами сущностей.
10. Проверь YAML/JSON и выбранную версию AsyncAPI валидатором; зафиксируй результат.

## Формат результата

- AsyncAPI YAML/JSON в версии, принятой проектом.
- Описание приложения и протокола.
- Таблица каналов/topics и операций (send/receive).
- Таблица сообщений: name/type, headers, payload, key/correlation, schema.
- Описание retry/error/DLQ/delivery guarantees — только если подтверждены.
- Результаты проверки и открытые вопросы.

## Чек-лист самопроверки перед PR

- [ ] Прочитаны актуальная Jira Story, критерии приёмки и релевантные связанные задачи.
- [ ] Проверены `knowledge` и статусы всех используемых допущений.
- [ ] Каждое существенное требование и проектный факт имеет источник.
- [ ] Термины, имена сущностей, сервисов, API и статусы согласованы с источниками.
- [ ] Нет придуманных требований, полей, состояний, переходов, компонентов или интеграций.
- [ ] Диаграмма/документ соответствует выбранной нотации и версии формата.
- [ ] Артефакт согласован с другими затронутыми артефактами либо расхождения явно перечислены.
- [ ] Все открытые вопросы и допущения явно обозначены; блокирующие вопросы вынесены пользователю.
- [ ] Проверены ссылки, имена файлов, синтаксис и возможность открыть/проверить результат доступными средствами.
- [ ] Diff содержит только изменения в рамках задачи; секреты и персональные данные не добавлены.
- [ ] PR описывает изменения, источники, проверки и известные ограничения.
- [ ] Создание PR/push выполняется только при наличии прав и прямого разрешения пользователя.
- [ ] `key` объявлен в **message-binding** (`components.messages.*.bindings.kafka.key`), а не в binding операции.
- [ ] `messageId` не задан там, где одно сообщение используется и в `publish`, и в `subscribe` одного канала — иначе строгий валидатор видит дубль.
- [ ] Прогнаны **два валидатора**: AsyncAPI CLI и строгий (Swagger Editor / AsyncAPI Studio); расхождения между ними зафиксированы в отчёте проверки.

Если обязательная проверка не пройдена, не называй артефакт готовым к PR. Укажи, что именно осталось.


### Дополнительная проверка для этого skill

Проверь направление send/receive, channels, message references, schemas, bindings, payload/header consistency, event names, key и отсутствие выдуманных гарантий доставки.

## Чего делать нельзя

- Не выдумывай бизнес-факты, правила, метрики, роли, интеграции, статусы, поля или сценарии.
- Не используй общие знания модели или интернет как источник требований конкретного проекта.
- Не выдавай реализацию в коде за утверждённое требование.
- Не повышай неподтверждённое допущение до требования без подтверждения.
- Не устраняй противоречия между Jira и `knowledge` молча.
- Не клади `key`, `schemaId` и прочие поля сообщения в binding операции: в Kafka operation-binding допустимы только `groupId`, `clientId`, `bindingVersion`.
- Не дублируй `messageId`, если одно сообщение переиспользуется в каналах.
- Не считай проверку законченной после одного валидатора: CLI пропускает часть ошибок структуры биндингов.
- Не меняй версии спецификаций, стиль и структуру проекта без основания.
- Не добавляй необязательную сложность «на всякий случай».
- Не удаляй и не перезаписывай существующие артефакты без необходимости и согласования.
- Не изменяй Jira, код, схемы БД или интеграционные настройки, если задача просит только анализ/документирование.
- Не утверждай, что тест, валидация, push или PR выполнены, если это фактически не подтверждено.

## Правила проекта (из замечаний пользователя)

Применяются всегда; при конфликте приоритет выше общих рекомендаций навыка.

- **R-07.** Одно имя на один смысл: статусы, поля и события совпадают с `knowledge` и другими артефактами.
- **R-09.** AsyncAPI: `key` — в message-binding; `messageId` не дублировать; проверять CLI и строгим валидатором.
- **R-11.** Каждая диаграмма в артефактах имеет рендер (SVG/PNG), а не только исходник.
- **R-13.** Перед сдачей сверять `knowledge` и артефакты по статусам, лимитам и именам; расхождения устранять.
- **R-14.** Не генерировать код через PowerShell here-string: backticks ломают содержимое. Писать файл целиком.

Полный перечень правил: `skills/PROJECT-RULES.md`, обоснование — `ai-log.md`.

## Проверка артефакта

**Инструмент:** AsyncAPI CLI `validate` **и** строгий валидатор (Swagger Editor / AsyncAPI Studio)

**Обязательный шаг:** создать `artifacts/asyncapi-<фича>-check.md`. В отчёте:

1. самопроверка по чек-листу навыка — пункт за пунктом;
2. команда проверки и её фактический вывод (код возврата, число ошибок);
3. что проверка **не** подтверждает;
4. как воспроизвести проверку.

## Источники и публикация

- **Требования:** прочитать карточку Jira через MCP — описание, критерии приёмки, связи,
  комментарии. Не работать по пересказу.
- **Проверка:** инструмент из раздела «Проверка артефакта», отчёт `<артефакт>-check.md`.
- **Публикация:** ветка и Pull Request через MCP GitHub. Первый коммит — `agent: draft <артефакт>`,
  правки — `review: ...`.

### Правила из ревью Ф2 (E-10, E-17, E-18)

- **Кавычки в YAML.** Значение с `: ` (двоеточие и пробел) пишется в кавычках или блочным
  текстом (`|`). Иначе парсер падает: `Incomplete explicit mapping pair`.
- **Валидатор до коммита.** После любой правки описаний прогонять `asyncapi validate` и
  читать вывод целиком. Ошибка парсера — стоп, а не «потом поправлю».
- **Направление операций.** Пишем на AsyncAPI **3.0** и используем `send` / `receive`
  с точки зрения описываемого сервиса: `send` — сервис публикует, `receive` — сервис читает.
  Формулировка «все события в publish» направление не передаёт.
- **Политика повторов — своя у событий.** `1 / 5 / 15 минут` из `AS-17` относится к вызовам СБП,
  а не к доставке событий. Для событий — своя политика (`AS-20`: секунды) и отдельный DLQ.
