# Правила проекта

Каждое правило выведено из конкретного замечания пользователя. Нарушение считается ошибкой,
даже если правило раньше не нарушалось. Обоснование и контекст — в `ai-log.md`.

| ID | Правило |
|---|---|
| R-01 | Пример из чужой работы — «хорошее решение», а не эталон. Не превращать его в обязательное требование. |
| R-02 | Не переносить замечания к прошлым работам на текущий артефакт. |
| R-03 | В задаче описывается результат, а не реализация: без имён событий, топиков, таблиц и эндпоинтов. |
| R-04 | AC — у истории, DoD — у задачи. AC задачи не дублирует AC истории. |
| R-05 | В истории не перечислять задачи текстом: связи `relates` достаточно. |
| R-06 | Не выдумывать измеримые критерии (SLO, тайминги), если их нет в требованиях. |
| R-07 | Одно имя на один смысл: статусы, поля и события совпадают с `knowledge` и другими артефактами. |
| R-08 | Технический сбой не равен блокировке по данным: разные статусы и разные действия. |
| R-09 | AsyncAPI: `key` — в message-binding; `messageId` не дублировать; проверять CLI и строгим валидатором. |
| R-10 | Термины как в проекте: `API Gateway`, а не «API-шлюз». |
| R-11 | Каждая диаграмма в артефактах имеет рендер (SVG/PNG), а не только исходник. |
| R-12 | Перед вердиктом читать все задачи по теме, всю `knowledge` и смежные артефакты. |
| R-13 | Перед сдачей сверять `knowledge` и артефакты по статусам, лимитам и именам; расхождения устранять. |
| R-14 | Не генерировать код через PowerShell here-string: backticks ломают содержимое. Писать файл целиком. |
| R-15 | Не выбирать за пользователя продукт, фичу, структуру задач — выносить вариант на подтверждение. |
| R-16 | Все изменения — через ветку и PR: первый коммит `agent: draft`, правки — `review: ...`. Прямой коммит в `main` не используется. |
| R-17 | Повторный вызов внешней системы — с тем же ключом идемпотентности, что и первая попытка. |
| R-18 | Числа в отчёте проверки совпадают с фактическим выводом инструмента. |
| R-19 | В сценарии отражены все статусы сущности из базы знаний, включая промежуточные. |
| R-20 | Бизнес-отказ и техническая ошибка — разные ветки: отказ не повторяется. |
| R-21 | Недоступность внешней системы — отдельная ветка с числом попыток и исходом. |
| R-22 | Бизнес-исход выплаты тоже публикуется событием: потребители узнают о результате без открытия экрана. |

## Как применяются

- Правила продублированы в `SKILL.md` тех навыков, где они чаще всего нарушаются.
- Перед сдачей артефакта — сверка по `R-07` и `R-13`: статусы, лимиты и имена между
  `knowledge` и каждым артефактом.
- Новое замечание пользователя сначала записывается правилом, потом исправляется артефакт.
