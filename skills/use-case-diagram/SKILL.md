# Skill: UML Use Case Diagram

## Когда применять

Применяй, когда нужно показать функциональные возможности системы с точки зрения пользователей и внешних акторов, определить scope и связи между целями.

## Что взять на вход

### Обязательный вход
1. **Story / задача Jira**: ключ, summary, описание, критерии приёмки, комментарии с решениями, связанные задачи и ссылки на Epic (если имеются).
2. **Knowledge**: релевантные разделы `knowledge/README.md`, `01-glossary.md`, `02-business-rules.md`, `03-assumptions.md`.
3. **Запрос пользователя**: какой результат нужен, для кого, в каком формате и в каких границах.

### Дополнительный вход
- существующие диаграммы и спецификации;
- ограничения и стандарты проекта, зафиксированные в Jira или `knowledge`;
- фактическая структура репозитория и выбранные форматы файлов;
- связанные требования и решения.

Если Jira Story для задачи не существует, не выдумывай её: используй явно указанный пользователем контекст и отметь ограничение. Если входных данных недостаточно для достоверного результата, сначала задай вопрос.

## Общие правила источников

- Факты о конкретном проекте и требованиях бери только из Jira и `knowledge`, согласно корневому `AGENTS.md`.
- `knowledge/03-assumptions.md` используй с учётом статуса каждого допущения: неподтверждённое допущение не является утверждённым требованием.
- Репозиторий и код используй для определения существующей структуры, форматов и фактической реализации. Не выводи из реализации новые бизнес-требования.
- Официальные спецификации (например, OpenAPI, AsyncAPI, BPMN, UML, C4, DBML) используй только для корректности нотации и формата, а не как источник фактов о проекте.
- Для существенных утверждений сохраняй ссылку на Jira issue key или путь к документу `knowledge`.
- Если источники отсутствуют, недоступны или противоречат друг другу, обозначь пробел и задай конкретный вопрос. Не заполняй его догадкой.

## Шаги работы

1. Определи систему в фокусе и её границу.
2. Из Jira и `knowledge` извлеки роли/внешние системы и цели, которые они достигают через систему.
3. Формулируй use case как цель/результат пользователя, а не как экран, таблицу или внутреннюю функцию.
4. Размести акторов вне границы системы, варианты использования — внутри.
5. Добавляй связи association, `include` и `extend` только при обоснованной семантике; не используй их как декоративные стрелки.
6. Для важных use case подготовь краткие сценарии: инициатор, предусловия, основной поток, альтернативы/исключения, постусловия.
7. Не смешивай бизнес-роли с техническими сервисами без основания.
8. Проверь, что все акторы и use case подтверждены источниками.

## Формат результата

- Контекст и граница системы.
- UML Use Case Diagram (редактируемый исходник в принятом формате).
- Перечень акторов и их целей.
- Краткие описания ключевых use case: предусловия, основной поток, альтернативы, результат.
- Связь use case с Jira Story/критериями приёмки.
- Открытые вопросы.

## Чек-лист самопроверки перед PR

- [ ] Прочитаны актуальная Jira Story, критерии приёмки и релевантные связанные задачи.
- [ ] Проверены `knowledge` и статусы всех используемых допущений.
- [ ] Каждое существенное требование и проектный факт имеет источник.
- [ ] Термины, имена сущностей, сервисов, API и статусы согласованы с источниками.
- [ ] Нет придуманных требований, полей, состояний, переходов, компонентов или интеграций.
- [ ] Диаграмма/документ соответствует выбранной нотации и версии формата.
- [ ] Артефакт согласован с другими затронутыми артефактами либо расхождения явно перечислены.
- [ ] Все открытые вопросы и допущения явно обозначены; блокирующие вопросы вынесены пользователю.
- [ ] Проверены ссылки, имена файлов, синтаксис и возможность открыть/проверить результат доступными средствами.
- [ ] Diff содержит только изменения в рамках задачи; секреты и персональные данные не добавлены.
- [ ] PR описывает изменения, источники, проверки и известные ограничения.
- [ ] Создание PR/push выполняется только при наличии прав и прямого разрешения пользователя.

Если обязательная проверка не пройдена, не называй артефакт готовым к PR. Укажи, что именно осталось.


### Дополнительная проверка для этого skill

Проверь системную границу, правильное положение акторов/use cases и корректность include/extend; все цели должны быть понятны пользователю.

## Чего делать нельзя

- Не выдумывай бизнес-факты, правила, метрики, роли, интеграции, статусы, поля или сценарии.
- Не используй общие знания модели или интернет как источник требований конкретного проекта.
- Не выдавай реализацию в коде за утверждённое требование.
- Не повышай неподтверждённое допущение до требования без подтверждения.
- Не устраняй противоречия между Jira и `knowledge` молча.
- Не меняй версии спецификаций, стиль и структуру проекта без основания.
- Не добавляй необязательную сложность «на всякий случай».
- Не удаляй и не перезаписывай существующие артефакты без необходимости и согласования.
- Не изменяй Jira, код, схемы БД или интеграционные настройки, если задача просит только анализ/документирование.
- Не утверждай, что тест, валидация, push или PR выполнены, если это фактически не подтверждено.
