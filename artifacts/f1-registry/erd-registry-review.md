## 🟡 Стоит улучшить

### S-01. Нет места для `eventId` — идемпотентность событий не обеспечена данными

- **Где:** `schema-registry.sql` — нет таблицы обработанных событий; `asyncapi-registry.yaml` —
  описание «обработчик проверяет `eventId`».
- **Что не так:** AsyncAPI требует защиты от повторной обработки по `eventId`, но в модели нет
  ни таблицы `processed_events`, ни поля, куда этот идентификатор записывается.
- **Почему это ошибка:** `AS-13` требует идемпотентности, а без хранилища проверка невозможна.
  Артефакты противоречат друг другу: событие «защищено», а сохранить факт обработки некуда.
- **Как исправить:** добавить таблицу `processed_events (event_id uuid primary key, consumer
  text not null, processed_at timestamptz not null)` и запись в одной транзакции со сменой
  статуса реестра.
- **Серьёзность:** 🟡 (до реализации, но расхождение с AsyncAPI явное).

### S-02. Дубли ИНН не отбиваются базой

- **Где:** `payout_rows`, индекс `payout_rows_inn_idx` (обычный, не уникальный).
- **Что не так:** `O-08` запрещает два одинаковых ИНН в одном реестре, но на уровне БД это
  не ограничено — защита живёт только в коде валидации.
- **Почему важно:** при гонке двух процессов проверки или ручной вставке дубль пройдёт.
- **Как исправить:** частичный уникальный индекс
  `UNIQUE (registry_id, inn) WHERE status = 'VALIDATED'` — отклонённые строки не мешают,
  а принятые дубли невозможны.
- **Серьёзность:** 🟡.

### S-03. Нет индекса для отчёта по результатам выплаты

- **Где:** `payouts`, индекс только по `status`.
- **Что не так:** отчёт по реестру (`SCRUM-2192`) читает выплаты по `registry_id`, а индекса
  по нему нет.
- **Почему важно:** на реестре в 5 000 строк отчёт будет последовательным сканированием.
- **Как исправить:** добавить `CREATE INDEX payouts_registry_idx ON payouts (registry_id)`.
- **Серьёзность:** 🟡.
