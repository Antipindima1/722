# AsyncAPI — события реестра выплат (Ф1)

- **Артефакт:** `artifacts/feature-registry-check/asyncapi-registry.yaml` (AsyncAPI 3.0.0)
- **Фича:** Ф1 — `SCRUM-2187`, истории `SCRUM-2189`, `SCRUM-2190`
- **Проверка:** AsyncAPI CLI `validate`
- **Дата:** 2026-11-17

## Каналы

| Канал | Публикует | Читает | Зачем |
|---|---|---|---|
| `registry.uploaded` | Сервис реестров | воркер проверки (`registry-validation-worker`) | запустить асинхронную проверку после загрузки |
| `registry.checked` | Сервис реестров | Сервис выплат, Сервис уведомлений | сообщить результат проверки и счётчики |
| `registry.validation-failed` | Сервис реестров | Сервис уведомлений, поддержка | сообщить, что проверка не состоялась по технической причине |
| `registry.revalidation-requested` | Сервис реестров | воркер проверки | повторно проверить реестр после устранения причины |
| `registry.events.dlq` | Сервис реестров | ручной разбор | сохранить недоставленное событие |

## Принятые решения

| Решение | Почему так | Источник |
|---|---|---|
| Ключ сообщения — `registry_id` | события одного реестра должны идти в одной партиции и в правильном порядке | `AS-17`, `AS-18` |
| `eventId` в каждом сообщении | защита от повторной обработки при повторной доставке | `AS-13` |
| Публикация «реестр проверен» отдельным событием | сервис выплат не должен опрашивать реестр | `CHK-09` |
| DLQ-канал для недоставленных | после исчерпания попыток нужен разбор, а не потеря | `AS-20` |
| Причина отказа в `RegistryValidationFailed` — enum | клиент различает «нет файла», «таймаут», «внутренняя ошибка» | `CHK-01` |
| Статусы в payload — те же, что в OpenAPI | сквозная согласованность артефактов: `CHECKED`, `BLOCKED`, `VALIDATION_FAILED` | `02-business-rules.md` §4.1, `AS-19` |

## Надёжность

- Повторная доставка: обработчик проверяет `eventId` и не применяет событие дважды (`AS-13`).
- Направление операций задано явно: `send` там, где сервис реестров публикует, `receive`
  там, где читает воркер (`AsyncAPI 3.0`).
- Доставка событий описана машинно: `x-delivery-policy` — `maxAttempts: 3`,
  `backoffSeconds: [1, 5, 15]`, `dlqChannel: registryDlq`, источник `AS-20`.
- Ключ партиционирования объявлен как **message binding** (`bindings.kafka.key`), а не как
  binding операции: в Kafka operation-binding поле `key` недопустимо.
- События публикуются после коммита состояния реестра, чтобы не объявить статус, которого
  ещё нет в базе.
- Порядок внутри реестра гарантируется ключом партиционирования.

## Трассировка

| Критерий / правило | Где в спецификации |
|---|---|
| Реестр принят и проверяется (`SCRUM-2189`) | канал `registry.uploaded`, статусы `UPLOADED`, `VALIDATING` |
| Отчёт о проверке (`SCRUM-2190`) | канал `registry.checked`, счётчики `acceptedCount`, `rejectedCount`, `errorShare` |
| Блокировка при превышении доли ошибок (`AS-14`) | статус `BLOCKED` в `RegistryCheckedPayload` |
| Идемпотентность обработки (`AS-13`) | поле `eventId` |
| Ретраи и DLQ (`AS-20`) | канал `registry.events.dlq`, описание повторов |

## Открытые вопросы

| Вопрос | Почему открыт |
|---|---|
| Email и лицензия проекта | неизвестны; в спецификации их нет, чтобы не выдумывать. Валидатор даёт по ним 2 предупреждения |
| Нужен ли отдельный канал для повторной проверки реестра | сценарий повторной загрузки пока не описан в требованиях |
| AsyncAPI 3.0 | выбран как стандарт проекта: `send` и `receive` однозначно задают направление операции |
| `messageId` в сообщениях | не задаётся: сообщение переиспользуется в нескольких операциях, а строгий валидатор считает одинаковый `messageId` дублем |
