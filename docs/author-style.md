# Правила подачи артефактов

Назначение: как оформлять артефакты и отчёты о проверке, чтобы их принимали с первого круга.
Правила выведены из практики ревью проекта; конкретные лица, площадки и чужие проекты
не упоминаются. Примеры — из «ВыплатыПро».

Это ориентир, а не обязательный стандарт: если правило противоречит Jira или `knowledge`,
приоритет у источников.

## 1. Формат отчёта о проверке

1. **Общее впечатление** — принято / принято с замечаниями / не принято и почему.
2. **✅ Что получилось хорошо** — перечисление с пояснением.
3. **🔴 Критичное (требует исправления)** — по каждому пункту: *Что не так → Почему важно →
   Как исправить*.
4. **🟡 Стоит улучшить** — то же в три шага, но не блокирует приёмку.
5. **🔗 Связность с другими артефактами** — согласованы ли статусы, события и имена.

Отчёт в другой структуре читается как чужой: замечания теряются.

## 2. Что требуется от каждого типа артефакта

### C4

- Уровни L1 и L2; на L2 при большом числе сервисов — группировка «сервис + его БД».
- Каждый контейнер назван по функции, а не «Backend».
- У каждой связи — протокол; если контракт не задан, это написано явно.
- Технология указывается, только если подтверждена; иначе — допущение с номером `AS-xx`.
- Персональные данные: где маскируются или шифруются.
- Таблица компонентов: Название | Назначение | Основные функции | Взаимодействия.

### Sequence

- Участники названы по функции, lifeline используются корректно.
- **На стрелках — данные**: путь и ключевые поля либо имя события. Плохо: `POST`, `SQL`,
  `200 OK`. Хорошо: `POST /registries {file, Idempotency-Key}`.
- Синхронные и асинхронные вызовы различаются.
- Сервис не пишет в чужую БД — только через сервис-владелец.
- Долгие операции не держат HTTP: `202 Accepted` и опрос статуса или push.
- Повторы: конкретные интервалы, только технические сбои, тот же ключ идемпотентности.
- Порядок операций: сначала сущность (реестр в статусе «Проверяется»), потом действие
  (проверка строк), иначе действие существует без основания.

### OpenAPI, AsyncAPI, ER

- Раздел **кэширование**: что кэшируется, почему снижает нагрузку, как сбрасывается (ETag).
- Раздел **повторы и защита от повторной обработки**: условия, число попыток, задержки, DLQ.
- Статусы согласованы между спецификациями, диаграммами и базой знаний.
- Для идемпотентности нужна опора в данных: ключ в таблице, `processed_events` для событий.
- Ошибки: HTTP-код плюс машиночитаемый код, а не только текст сообщения.
- `GET` списков — фильтры и пагинация (`limit/offset`, `total`).
- Авторизация: что именно проверяет сервис и какие коды возвращает.
- Повторное создание: поведение при том же теле и при другом теле различается.

### Декомпозиция

- Задача — работа на 1–2 спринта, а не «тема».
- Границы MVP согласованы с постановкой: нельзя вынести в поздние спринты то, без чего
  фича не работает.
- Порядок зависимостей: контракты раньше реализации, модель данных раньше выплат.

## 3. Сквозные принципы

| Принцип | Формулировка |
|---|---|
| Измеримость | любая цель имеет число и обоснование |
| Конкретика вместо заглушек | «уточним позже» недопустимо в сдаваемом артефакте |
| Данные на связях | на стрелках и в таблицах — поля, пути, имена событий |
| Границы ответственности | сервис не обращается к чужой БД |
| Асинхронность по умолчанию | долгие операции — `202` и опрос, а не удержание соединения |
| Согласованность | статусы и события совпадают во всех артефактах |
| Нет пустых разделов | пустой раздел = незакрытое требование |
| Аккуратность текста | опечатки и битые ссылки снижают доверие к документу |

## 4. Чек-лист перед сдачей

- [ ] Разделы пронумерованы, есть оглавление.
- [ ] Требования — таблицей с ID и колонкой «Обоснование».
- [ ] Статусы — таблицей «статус / переходы / условие», конечные помечены.
- [ ] Участники и контейнеры названы по функции.
- [ ] У каждой связи есть протокол, у каждого шага — данные.
- [ ] Каждое утверждение опирается на Jira или `knowledge`; иначе вынесено как допущение.
- [ ] Нет пустых разделов и заглушек.
- [ ] Числа (лимиты, интервалы, тайминги) взяты из источников, а не придуманы.
