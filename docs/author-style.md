# Как автор пишет артефакты и по каким критериям их принимают

Источники: 10 сданных работ автора в Confluence, **11 комментариев ревью** в Jira
(`SA-2270…SA-2275`): 6 от бота `Automation for Jira` и 5 от ментора (Стецюк Владимир).

Это референс, а не эталон. Ниже — что повторяется из ревью в ревью и что из этого мы
применяем к артефактам «ВыплатыПро».

## 0. Формат ревью, к которому привыкли

Бот ревьюит по одной схеме, и ментор её же повторяет («продолжу по схеме моего ИИ коллеги,
чтоб было привычнее»):

1. **Общее впечатление** — принято / не принято и почему.
2. **✅ Что получилось хорошо** — перечисление с пояснением.
3. **🔴 Критичное (требует исправления)** — по каждому пункту: *Что не так → Почему важно →
   Как исправить*.
4. **🟡 Стоит улучшить** — то же в три шага, но не блокирует приёмку.
5. **🔗 Связность с другими артефактами** — наследует ли артефакт предыдущие.

Вывод: наш `smotryashchiy` должен выдавать отчёт **в этой же структуре**, иначе замечания
воспринимаются как чужие.

## 1. Что ревью требует от каждого типа артефакта

### Vision

- KPI измеримые, **с обоснованием** («не более 2 минут у 95% сессий», а не «быстро»).
- Для каждого риска — способ снижения, в том числе организационный (резервный эквайринг).
- Блок «Описание значимости артефакта» заполнен — это criterion приёмки, а не украшение.
- Опечатки в заголовках режут глаз: «Заинтерисованные» → «Заинтересованные».

### BRD

- Таблица бизнес-требований обязательна: **ID | Формулировка | Обоснование | Шаг процесса**.
- Жизненные циклы обязательны: Бронирование, Поездка, Залог/Платёж, Кейс повреждения.
- Метрики с обоснованием; **ожидания по нагрузке — конкретные цифры**.
  Дословно: «Senior SA должен уметь делать обоснованные допущения, если точных данных нет».
- BPMN-диаграммы должны соответствовать требованиям, а не жить отдельно.

### C4

- L1 + L2; на L2 при большом числе сервисов — **группировка через Boundary** (сервис + его БД).
- API Gateway: упомянуть **Circuit Breaker / Rate Limiting** для системы с внешними интеграциями.
- Персональные данные: указать **шифрование PII** в БД.
- Таблица компонентов: Название | Назначение | Основные функции | Взаимодействия (с протоколом).

### Sequence

- Участники названы **по функции**, не «Backend».
- **На стрелках — данные**: путь и ключевые поля или имя события. Дословно: «это требование
  DoD». Плохо: `POST`, `SQL`, `200 OK`. Хорошо: `POST /api/v1/bookings {car_id, Idempotency-Key}`.
- Синхронные и асинхронные стрелки различаются; lifeline используются корректно.
- Сервис **не пишет в чужую БД** — только через сервис-владелец.
- Webhook — отдельный входящий вызов, а не «ответ» на наш запрос.
- Долгие операции не держат HTTP: создаём `PENDING_HOLD`, отвечаем `202 Accepted`, результат —
  опросом `GET` или push.
- Повторы: конкретика интервалов («3 попытки: 2 с, 4 с, 8 с»), повтор только технических
  сбоев, с тем же `Idempotency-Key`. Отказ банка не повторяем.
- Порядок операций: сначала сущность (поездка), потом действие (открытие авто), иначе
  «машина открыта без поездки».

### OpenAPI / AsyncAPI / ER

- Раздел **кэширование**: что кэшируется, почему снижает нагрузку, как сбрасывается (ETag).
- Раздел **retry и защита от повторной обработки**: условия, число попыток, задержки, DLQ,
  что если событие пришло после истечения срока.
- **Пустых разделов быть не должно** — «Раздел 2.2.3 пустой. Описать…».
- Статусы согласованы между OpenAPI, ER и Sequence: «событие `BookingExpired` есть, а статуса
  `EXPIRED` нет — в enum `TIMING`».
- Для идемпотентности нужна опора в данных: таблица `processed_events`, запись в одной
  транзакции со сменой статуса, либо явное `UPDATE … WHERE status = 'PENDING_HOLD'`.
- Каждое действие с внешним эффектом имеет контракт: «чем именно инициирует освобождение
  холда? ни события, ни метода».
- `GET` списков — фильтры и пагинация (`limit/offset` или курсор, `total`/`next_cursor`).
- Авторизация: прямо указать, что проверяет сервис, и коды (404/403 для чужой брони),
  из каких статусов разрешена отмена и что возвращает повторная отмена.
- Идемпотентность создания: поведение при повторе с тем же телом (та же бронь, 200/202) и с
  другим телом (409/422).

### Декомпозиция

- Задача = работа на 1–2 спринта, а не «тема». В спринте 10–30 задач по ролям.
- Границы MVP согласованы с Vision: нельзя вынести в поздние спринты то, без чего не провести
  пилот (уведомления, кейсы повреждений, портал поддержки).
- Порядок зависимостей: эквайринг раньше холда, хранилище раньше загрузки фото, геозоны
  раньше проверки завершения поездки.
- Сквозной тонкий сценарий собирается рано (5–6 спринт), с заглушками, а не «всё сразу к 11-му».

## 2. Сквозные принципы, которые повторяются везде

| Принцип | Формулировка из ревью |
|---|---|
| Измеримость | любая цель и KPI имеют число и обоснование |
| Конкретика вместо заглушек | «конкретные значения пока не предоставлены» — недопустимо для Senior |
| Данные на связях | на стрелках и в таблицах — поля, пути, имена событий |
| Границы ответственности | сервис не лезет в чужую БД |
| Асинхронность по умолчанию | долгие операции — 202 + опрос/push, а не удержание HTTP |
| Согласованность артефактов | статусы и события совпадают в OpenAPI, ER, Sequence |
| Никаких пустых разделов | пустой раздел = незакрытое требование |
| Описание значимости | блок заполняется полностью, это AC |
| Аккуратность текста | опечатки снижают доверие к документу |

## 3. Что применяем к «ВыплатыПро»

| Требование | Состояние |
|---|---|
| Названия по функции, протоколы, трассировка к требованиям | ✅ есть |
| C4: L1 контекст | ❌ добавить |
| C4: Boundary — сервис вместе со своей БД | ❌ добавить |
| C4: Gateway с Rate Limiting / Circuit Breaker | ❌ добавить упоминание |
| C4: шифрование ПДн (у нас `AS-15`) | ❌ добавить в описание |
| Публикация в Kafka через Outbox, а не «сервис умеет» | ❌ добавить Outbox Publisher |
| Sequence: данные на стрелках, 202 + опрос, конкретные интервалы ретраев | применим, когда дойдём |
| OpenAPI: кэширование, retry/processed_events, без пустых разделов | применим |
| Отчёт ревью в формате 🔴/🟡/✅ | применим в `smotryashchiy` |

## 4. Чек-лист «как пишет автор»

- [ ] Разделы пронумерованы, есть оглавление, ссылки вида `BRD 7.3.1`.
- [ ] Требования — таблицей с ID и колонкой «Обоснование».
- [ ] Статусы — таблицей «статус / переходы / условие», конечные помечены.
- [ ] Участники и контейнеры названы по функции.
- [ ] У каждой связи есть протокол, у каждого шага — данные.
- [ ] Публикация в брокер — через Outbox/воркер.
- [ ] Каждое утверждение опирается на требование; нет — выносится как допущение.
- [ ] Нет пустых разделов и заглушек «уточним позже».
- [ ] KPI и нагрузка — с числами и обоснованием.
