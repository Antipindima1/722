# Процесс работы с репозиторием

Правило: любое изменение попадает в `main` только через ветку и Pull Request. Прямой коммит
в `main` не используется — иначе в истории не видно, где черновик агента, а где правки
человека по ревью.

## 1. Ветка

```
feat/<артефакт>-<фича>     feat/openapi-registry
fix/<что исправляем>       fix/ddl-inn-checksum
chore/<что делаем>         chore/pr-process
```

## 2. Коммиты

| Когда | Префикс | Пример |
|---|---|---|
| Первый коммит ветки — результат агента «как есть», без правок | `agent: draft` | `agent: draft openapi registry feature` |
| Исправления после проверки инструментом | `fix:` | `fix(api): add payout existence check` |
| Исправления после ревью | `review:` | `review: rewrite ai-log around agent errors` |
| Документация и отчёты | `docs:` | `docs(check): spectral output after fixes` |

Требование: первый коммит ветки — **черновик агента**. Правки человека идут отдельными
коммитами с `review:` в начале сообщения. Смешивать нельзя: по истории должно быть видно,
что агент сделал сам, а что исправлено после ревью.

## 3. Pull Request

В описании PR:

1. что входит в изменения (файлы и их назначение);
2. источники: ключи Jira, файлы `knowledge`;
3. проверки: инструмент, команда, результат (код возврата, число ошибок);
4. ревью: вердикт и что исправлено;
5. известные ограничения.

После мержа ветка удаляется, ссылка на PR остаётся в задаче Jira.

## 4. Связь с Jira

- Ссылка на PR и на файлы артефактов добавляется в карточку или комментарий к ней.
- Статусы и описания в Jira меняются только по прямому поручению пользователя.

## 5. Исключения

Быстрая правка опечатки в документации — тоже через PR: исключений нет, иначе правило
перестаёт работать. Если PR невозможен технически (нет прав, недоступен GitHub), результат
готовится локально, а ограничение фиксируется явно.
